# 技术设计：add-traceable-vector-retrieval

本文件记录本课实现中**有多个可选做法、需要写清取舍**的决策。规约（
`specs/knowledge-retrieval/spec.md`）规定"必须做到什么"，本文件说明"为什么这样做"。

---

## 决策 1：切片正文存 MySQL，向量存 Qdrant，靠主键关联

### 背景

要检索就得存向量，要展示出处就得取回正文。有两种常见做法：

| 做法 | 说明 |
|---|---|
| A. 正文与向量都放向量库 | payload 里直接带 `chunk_text`，一次查询拿到全部 |
| B. 正文留关系库，向量库只存向量与标识 | 命中向量主键后回 MySQL 取正文 |

### 决定

采用 **B**。

Qdrant 中每条点仅保存：

```
id      : <knowledge_chunks.id>          # 向量主键 = 切片主键
vector  : [0.013, -0.221, ...]           # 定长浮点向量（维度与 collection 一致）
payload : {
  class_id          : 3,
  material_id       : 17,
  knowledge_entry_id: 9,
  chunk_id          : 4211,              # 与 id 相同
  chunk_index       : 2
}
```

MySQL 的 `knowledge_chunks` 行保存 `chunk_text`、`chunk_index`、字符偏移、`class_id`、
`material_id`、`knowledge_entry_id`、`index_status`。

### 理由

1. **摘录只能有一个来源。** 摘录要求"取自 MySQL 的切片正文"。若正文同时存在于
   payload，两侧可能不一致（重建索引、预处理变更后尤其容易），届时无法判断该信哪一份。
2. **关键字检索不依赖向量库。** Qdrant 故障时 `keyword` 仍要能用，这条降级路径的前提是
   正文和全文索引都在 MySQL。
3. **纯检索场景下不需要整段正文。** 向量检索只需要向量与主键；把几百字正文塞进 payload
   只会成倍放大向量库体积。

### 被否决的方案

- **A（payload 带正文）**：省一次查询，但正文出现两份副本，且摘录来源不受控。
- **随机向量主键 + 映射表**：主键与切片解耦，回表前多一次查找，本课没有这个必要。
- **把全文索引也搬进检索引擎**：班级过滤与事务一致性都要重做，超出本课范围。

### 代价

每次向量命中都要多一次 MySQL 回表查询。这是有意接受的成本。

## 决策 2：向量路径回表时再核对一次班级

### 背景

班级隔离要求在检索侧完成，但向量库过滤与关系库过滤是两处独立配置。任何一侧漏加条件
都会漏数据。

### 决定

两处**都**加，且回表时用同一会话班级值再核对一次：

```
1. Qdrant search  → filter: { class_id: sessionClass }, limit: N
2. 得到向量主键列表
3. SELECT ... FROM knowledge_chunks
   WHERE id IN (...) AND class_id = sessionClass AND index_status = 'ready'
```

### 理由

纵深防御。即便将来有人改坏了 Qdrant 的 filter 表达式，回表查询仍会把其他班级的行
排除在外。反过来，若 Qdrant 侧正常而回表漏了条件，同样会漏。

### 被否决的方案

- **只在 Qdrant 过滤**：向量库的 filter 语法与业务字段耦合，改动风险高。
- **只在 MySQL 过滤**：`vector` 模式的候选集来自 Qdrant，若 Qdrant 不按班级过滤，
  返回的 topK 会被其他班级占满，本班内容根本进不了候选。

### 对外的错误语义

跨班级检索**不返回 403**，而是 HTTP 200 + 空 `hits`。

理由：403 会泄露"该资源存在，只是不属于你"，等于变相确认了其他班级的材料标题或存在
性。返回空命中与"本班确实没有相关内容"这两件事对调用方不可区分——这正是想要的。

代价是无法区分"权限不足"与"真的没有"。本课接受这个代价。

## 决策 3：三种切分策略，默认 auto

### 背景

切片是检索的最小单位。切片过长会混入多件不相关的事，过短会把一个完整句子拆散。

### 决定

| 策略 | 参数 | 断句优先级 |
|---|---|---|
| `auto` | 最大 800 字，重叠 80 字 | 空行 → 换行 → 句号 → 强制截断 |
| `custom` | 最大 100–2000 字，重叠 0%–50% | 分隔符 → 强制截断；可选预处理 |
| `hierarchy` | 沿用 auto 的长度上限 | `#` / `##` / `###` 分章，过长章二次切分 |

- **重叠的作用**：避免一句话正好落在窗口边界上被截断，导致两个切片各含半句、都检索不到。
  80 字 ≈ 800 字的 10%。
- **`custom` 的长度上界 2000**：超过这个量级，单个切片已经混入多个主题，检索精度下降；
  下界 100 是防止把一句话切碎成词组。
- **`hierarchy` 保留标题**：标题本身是强语义信号（"第二章 函数与极限"），把它单独切出去
  会让正文切片失去章节上下文。

### 预处理与原文的关系

移除 URL／邮箱、折叠连续空白等预处理**只作用于待切分与待嵌入的文本**，
`knowledge_entries.body_text` 保持上传原文。

**由此产生的坑**：切片偏移量是相对于**预处理后**文本计算的，不能再当作原文件中的
字符下标使用。前端按偏移高亮原文时必须知道这一点。

### 被否决的方案

- **按句子或语义边界切分**：切片长度不稳定，且需要额外的分句依赖。
- **子切片检索、父块送模型**：需要额外一次回表查询，本课不引入。
- **只对变更段落重新嵌入**：需要具备"判断哪一段变了"的能力（diff 或哈希），本课不做。

## 决策 4：hybrid 用 RRF 融合，而不是分数加权求和

### 背景

两条路径给出的分数不在一个尺度上：全文相关度是无上界的实数（ngram 打分的加权和），
余弦相似度落在 `[-1, 1]`。直接相加会让量级大的一路完全支配排序。

### 决定

采用 **RRF（Reciprocal Rank Fusion）**：

```
score(chunk) = Σ_paths  1 / (k + rank_path(chunk))
k = 60
```

若某条切片只在一条路径上出现，另一路不贡献分数（不是补 0 名次）。

### 理由

1. **只看名次，不看分数**：彻底回避量纲问题，换嵌入模型或换分词器时无需重新标定权重。
2. **两路都命中的切片自然靠前**：它会被累加两次倒数名次，符合直觉。
3. **`k = 60`**：来自 RRF 原始论文的经验值，作用是压低头部名次的绝对优势，避免某一路的
   第 1 名单独决定最终排序。

### 前置过滤

RRF 之前，两路各自先按绝对分数过滤：

- `vector` 路丢弃余弦 < 0.35 的候选；
- `keyword` 路按全文相关度取前若干条。

**名次分不是相关性阈值。**「在候选里排第 1」和「真的相关」是两件事：如果全部候选都不
相关，第 1 名照样是第 1 名。所以过滤必须发生在融合之前。

### 被否决的方案

- **归一化后加权求和**：换模型就要重调权重，且两路的分数分布未必同形。
- **只保留 hybrid**：Qdrant 一故障，关键字路径就无法单独降级使用了。
- **加交叉编码器重排序**：更准，但延迟明显上升，本课不实现。

## 决策 5：问答先检索再生成，无切片不调模型

### 决定

```
POST /api/ask
  ┌─ 取用户最新一句提问（历史对话附在其后）
  ├─ 本班 hybrid 检索，取前 4 条
  ├─ 有切片 → 组装 { 标题, 切片序号, 切片正文 } × N + 用户提问 → 对话网关
  │             回答正文以 [1] [2] 标注出处，顺序与 citations 一致
  └─ 无切片 → 直接返回「资料中未找到相关内容」，citations 为空，不调网关
```

### 为什么取 4 条

太少 → 依据不足；太多 → 无关切片混入，模型容易被噪声带偏，且 token 成本上升。
4 条是精度与召回的一个折中，也让 `[1]`–`[4]` 的标注在界面上放得下。

### 为什么无切片时绝不调模型

模型参数里没有本校讲义，但它是会**编**的。一旦在无依据时把问题交给它，回答就退化成
"凭记忆作答 + 看起来专业"，而这恰恰是 RAG 要解决的问题。此时唯一正确的输出是
"资料中未找到相关内容"。

注意：页面上出现一段文字，**不能**证明模型被调用过。`citations` 为空 + 固定文案才是
判据。

### system 提示的来源

客户端传入的 `role: system` 消息一律丢弃。约束（"只能依据编号对应的资料作答"）由服务端
写入，否则调用方可以通过注入 system 消息改写模型行为。

### 被否决的方案

- **无依据时调模型并要求它说"不知道"**：提示约束可能被忽略，不可靠。
- **无依据返回 404**：把"空结果"和"资源不存在"混为一谈。
- **把弱相关候选也塞给模型**：可追溯性下降，等于变相"凑数"。

## 决策 6：组件部署与端口暴露

### 拓扑

```
浏览器 ──→ Nginx ──/api──→ Go 服务
                             ├── 认证模块（请求先经此处）
                             ├── 材料模块（文件 + body_text）
                             └── 检索模块（切分 · 检索 · 回答编排）
                                    ├──→ MySQL     （会话、正文、切片文本、全文索引）
                                    ├──→ Qdrant    （仅向量与标识）
                                    ├──→ 嵌入网关  （文本 → 向量）
                                    └──→ 对话网关  （有切片时才调用）
```

### 端口暴露

| 组件 | 是否对外 | 说明 |
|---|---|---|
| Nginx | 是 | 唯一入口，`/api` 反代到 Go |
| Go 服务 | 否 | 仅容器内可达 |
| MySQL | 否 | 仅容器内可达 |
| **Qdrant** | **否** | **不得映射到宿主端口** |
| 嵌入网关 | 否 | 密钥留在服务端 |
| 对话网关 | 否 | 同上 |

### 为什么 Qdrant 坚决不暴露

Qdrant 自身不带业务鉴权。一旦把 6333 映射到宿主，任何人都能直接读走全部班级的向量与
payload——班级隔离形同虚设，而且不经过任何一次会话校验。

即便"只是为了让调试方便"，也必须通过服务端的调试接口做，而不是开端口。

### 密钥

嵌入与对话两类网关都需要密钥。密钥只存在于服务端环境变量，**不下发到浏览器**，
页面中不展示向量分量。

## 决策 7：重建索引是显式动作

### 决定

- 已入库材料**不会**自动重新切分；
- 教师调用重建接口时，**先删除旧切片与旧向量记录，再按本次请求中的策略重新写入**；
- 未指定策略时按 `auto`。

### 为什么先删后写

如果直接追加，旧切片与旧向量会残留。它们指向同一份材料，但切分边界已经不同，检索时
会出现互相矛盾的重叠片段，且 Qdrant 中会堆积再也回不到有效行的孤儿主键。

### 一个容易踩的坑

若 `custom` 策略中开启了"折叠连续空白为单个空格"，则换行符不复存在。之后再以换行作为
分隔符切分，将没有任何断点，全部退化为按最大长度强制截断。

**顺序是有影响的**：先预处理、再按分隔符切分。

### 被否决的方案

- **自动重建**：切分是要花嵌入调用的，每次改配置就全量重跑不可接受，且难以预期。
- **上传时策略与重建时策略强制一致**：剥夺了教师"换一种粒度试试"的能力。

## 降级矩阵

| 故障 | `keyword` | `vector` | `hybrid` | `POST /api/ask` |
|---|---|---|---|---|
| Qdrant 不可用 | 正常返回 | 503 | 503 | 503 |
| 嵌入服务不可用 | 正常返回 | 503 | 503 | 503 |
| 对话网关不可用 | — | — | — | 500 |
| 部分切片 `index_status = failed` | 跳过该切片 | 跳过该切片 | 跳过该切片 | 视命中情况而定 |
| 检索无候选 | 200 + 空 `hits` | 200 + 空 `hits` | 200 + 空 `hits` | 200 + 固定文案 |

**关键点**：`keyword` 路径**不依赖嵌入服务与 Qdrant**。只要 MySQL 活着，它就能返回
正文。这是整个降级设计的支点，也是"只保留 hybrid"这个方案被否决的原因。

**503 而不是空结果**：向量库挂了属于服务端故障，返回 503 让调用方知道"现在不能用"，
比返回空 `hits`（暗示"本班没有相关内容"）诚实。**不得编造相似度分数**来假装检索成功。

## 本课明确不做的

- 交叉编码器重排序（rerank）
- 流式输出
- 编排框架（LangChain / LlamaIndex / Dify）
- Qdrant 对外暴露
- 按班级拆分 Qdrant 集合（集合数随班级增长，运维成本不划算）
- 流式长对话（第 5 课）
